## Walk fixes 14–16, this session — the error-badge area, again

All three are in `src/card/picture-studio-card.ts`, all in the block that refuses
a native badge type outside `CORE_BADGES`.

**14 — the retry that retried nothing.** On a cold dashboard the card leaves the
item as a hole, primes `hui-error-badge`, and waited on `whenDefined` to call
`requestUpdate()`. That call could reach the hole through **neither** gate:
`updated()` only runs `_syncItems` when `_config` changed, and `_syncItems` only
rebuilds when the *shape* changed — `_renderedTypes` was identical. The badge
therefore never appeared until HA rebuilt the card (editor opened) or the config
changed, which is exactly what the user observed. Fix: the callback sets
`_renderedTypes = []` and calls `_syncItems()` itself. The old test asserted
`requestUpdate` had been called — green, guarding nothing.

**15 — the factory hands back HA's failure as our verdict.** Asking
`helpers.createBadgeElement({type:"error"})` routes into the unguarded
`ALWAYS_LOADED` branch, and when that fails HA **does not throw** — it catches and
returns an error badge carrying `n.setConfig is not a function`. A `try/catch`
around our call could never see it. That is the one-off the user photographed.
Fix: build the badge by hand (`document.createElement(ERROR_BADGE_TAG)` +
`setConfig`) behind the same guard, wrapped in a `try/catch` that falls back to a
hole. **No retry is armed in that catch** — the class was registered a line
above, so re-arming would rebuild into the same failure forever.

**16 — the console line now names the badge at fault.** The priming sentinel was
`"\x00"`, which does not print: the user saw `badge  Error: Unknown type
encountered:` with two blanks and reasonably read it as a bug. It is now
`PRIMING_TYPE = "picture-studio-priming"`, and `_primeErrorBadge` rewrites HA's
log **in place**, in HA's own shape, into
`badge state-label Error: Unsupported badge type: state-label` — the same string
the badge shows, built once as `const message`. The filter matches on the **type
argument**, never on message text, and `console.error` is restored in a `finally`
around a strictly synchronous call.

**The upstream issue is filed and already assigned** (user, 2026-08-21) on the
home-assistant/frontend repository. Its number is not recorded here — ask for it
and put it in the comment inside `_primeErrorBadge`, which today only says
"delete this once upstream ships the static import" and points at nothing.

**The fix benefits us with no release of ours.** The guard reads
`customElements.get(ERROR_BADGE_TAG)`; once the static import ships, the class is
defined before `loadCardHelpers()` returns, so the branch never runs — no priming,
no console line, no deferred rebuild, the badge drawn on the first pass. Users get
it as they update Home Assistant. **The HA floor governs only the *removal* of the
dead code, never the benefit** — and on this project raising the floor is cheap,
so do not treat the removal as far off.

**All of `_primeErrorBadge` is temporary.** When upstream statically imports
`hui-error-badge`, the class is defined before `loadCardHelpers()` returns, the
guard never fires, and the whole method plus `_awaitingErrorBadge` and
`PRIMING_TYPE` delete in one go. The issue text is at
**`captures/ha-frontend-issue-error-badge.md`** — git-ignored but inside the repo,
so it no longer dies with a session's `/tmp` scratchpad.

## The lesson of walk fixes 9–16

Eight consecutive fixes in one area. The recurring cause is **reasoning about an
expression instead of its dependencies** — and this session added the sharpest
instance: `requestUpdate()` was correct as an expression and inert as a
dependency, because two separate gates stood between it and the hole.

Three claims of mine were overturned by reading the shipped bundle rather than
arguing: that the 2000 ms timer might apply to our path (it is strictly inside the
`custom:` branch), that a `try/catch` could catch the failure (HA returns, it does
not throw), and that muting the console would swallow unrelated errors (the window
is one synchronous call, and the type argument filters exactly). **Read Home
Assistant's source before believing anything about it** remains the single most
productive habit here.
