**Two descriptions in the original wording were superseded and must not be
designed against.** The picker is not "move, resize and distort compose": `move`
is not an entry at all, because dragging the body always moves; the picker says

more than a picker — the anchor for every item, and the active tool's own
sub-tools.

What sub-project 4 needs from 1 is in the image spec's "Forward compatibility"
section and must be read before it is started; what it needs from 3 is the `Tool`

## The technique that settled this session: read the frontend bundle

**Three questions were answered and two committed spec claims were disproved by
reading Home Assistant's own shipped JavaScript out of the running container.**
Nothing else in this repository can answer "what does HA actually do", and the
project's oldest rule — never reimplement HA behaviour — is unenforceable
without it.

```sh
docker exec picture-studio-ha sh -lc \
  'ls /usr/local/lib/python3.14/site-packages/hass_frontend/frontend_latest'
```

The build number is the `home_assistant_frontend-<build>.dist-info` directory
beside `hass_frontend` in `site-packages`. **Pin every observation to it**, as
`has-changed.ts` and the error-badge workaround already do.

Traps, all of them cost time here:

- **`grep -o "pat.\{0,2000\}"` on a minified chunk hangs.** Greedy bounded
  repetition over megabyte-long lines does not finish. Use Python: read the file,
  `str.find`, slice. Copy the script in with `docker cp` — a heredoc through
  `sh -lc` mangles the quoting.
- **`.js.map` files here carry no `sourcesContent`.** There is no original source
  to recover; the minified chunk is the evidence.
- **Chunks are found by content, not by name.** `grep -rl "hui-image-element" *.js`
  gives the chunk; the class is then the text between the previous `class ` and
  the `(0,a.EM)("<tag>")` decorator call that registers it.

### `hui-image`'s order of precedence — measured 2026-08-25, build `20260729.6`

From its own `render()`, chunk `33932`:

```js
if (this.cameraImage) …                                  // ① wins over everything
else if (this.stateImage) {
  const t = this._resolvedStateImages[state];
  t ? s = t : (s = this._resolvedImageSrc, d = true);     // ② beats `image`, falls back to it
} else s = darkMode ? darkModeImage : … : this._resolvedImageSrc;   // ③
```

**`camera_image` → `state_image` → `image`.** The counter-intuitive part:
`image_entity` is NOT a branch of its own — our `imageSource` turns it into a
proxy URL and passes it as `.image`, so it sits in branch ③ and `state_image`
overrides it. Reading our own `imageSource` and assuming it described the whole
arbitration is exactly the mistake that shipped an inverted row label and a test
asserting the inversion.

**`state_image` is keyed by the entity's state *at render time*** — a table with
no entry for the current state falls back to `image`. So which branch wins is not
a property of the config, and nothing computed from config alone can track it.
That is why the item list names **what decides the picture**, not what is drawn
this second: a label that tracked it would flip between a name and a filename as
a door opens.

`window.loadCardHelpers` is `Promise.all([s.e(33932), s.e(58453), s.e(58251)])`,
and 33932 is the `hui-image` chunk — so its availability is **not** a side effect
of our background rendering, and no background misconfiguration can remove it.
It is still an internal with no deprecation cycle: guard with a lazy
`customElements.get`, the idiom `element-form.ts` already uses.

## What would bite someone cold

- **Decision 2 was argued wrong twice, from memory, before being measured.** Both
  times the conclusion happened to survive and the mechanism was false. If a
  claim about Home Assistant's internals matters, read the bundle; the cost is
  ten minutes and it is the difference between a spec and a plausible story.
- **`matrix3d` translations are pixels.** CSS accepts no percentage inside a
  matrix function, so a distortion does not rescale with the card and needs a
  `ResizeObserver`. **There is none anywhere in this repository** — it is a new
  mechanism for sub-project 3, not an idiom to copy.
- **Geometry is not form surface, and sub-project 1 breaks that on purpose.**
  Follow-up 9 states the rule: the form deliberately does not expose `top`/`left`.
  The image element's `width` / `height` / keep-ratio fields are **scaffolding**,
  removed at sub-project 2. Do not read them as a change of policy — and note
  that removing them takes away the only non-pointer way to size an image, so the
  keyboard path follow-up 9 owes has to cover **resize as well as move**. One
  design, not two.
- **`entity` and `image_entity` are different keys** and both appear in the form.
  `image_entity` *is* the picture; `entity` is the state that selects from
  `state_image` / `state_filter`. The card already carries both, in two sections.
- **`aspect_ratio` is the one background key an image element must not take.**
  Given one, `hui-image` builds its `.ratio` container — `height: 0` plus a
  padding box — which defeats the height the card imposes.

## The keep-ratio bug, and the four things it taught — 2026-08-25

Found in the browser **after** the whole feature was reviewed, green and ready to
merge. Fixed by `a8fd426`. What follows is the part that does not live in the
commit message.

### Home Assistant's number field emits on every keystroke

Typing `40` into a `selector: { number: … }` field commits **`4` first, then
`40`**. Anything that reads state during that window reads the intermediate
value. Here the card laid out at 4 %, the editor measured 4, and the form kept
that number until the user cleared keep-ratio — writing a height of 4 for a width
of 40. Every symptom was the first digit typed: 60 gave 6, and 15 and 17 both
gave 1, which looked like a floor and was not.

**The general rule this leaves behind: never capture a measurement into a
property. Pass a function.** A value has to be captured at some moment, and the
only moment available is a render — which is never the moment it is used.

### The dev setup delivers stale code, and a hard reload does not fix it

`.ha/config/.storage/lovelace_resources` registers the card as
`/local/picture-studio-card/picture-studio.js?v=N`, with **N fixed**. Rebuilding
`dist/` does not change the URL, so the browser keeps serving what it cached —
and "Empty cache and hard reload" did not reliably dislodge it either. **Bump N
in that file and restart the container** to deliver a new build; that is the only
method that proved reliable.

Related, and self-inflicted: **`rm -rf dist` breaks the Docker bind mount.**
`docker-compose.yml` binds `./dist` into the container, so deleting the directory
leaves the mount pointing at a dead inode and every resource 404s. Recreate the
directory and `docker compose restart homeassistant`.

### A debug overlay belongs inside the card, not on `document.body`

The edit dialog renders in the **top layer**, which no `z-index` can climb over —
an overlay on `body` is invisible exactly when it is needed. Mount it inside the
card's `.root`. Two follow-on traps, both hit: give each card **its own node**
(several picture-studio cards exist on a dashboard in edit mode, and a shared
singleton is stolen by whichever rendered last, usually the one behind the
dialog), and mirror every line to `console.log`, because an overlay with
`pointer-events: none` — which it must have, or the picture underneath stops
being draggable — cannot be selected or copied.

### Sub-project 2 makes this class of bug impossible, not merely fixed

Noted by the user and worth keeping: once the box is dragged by a handle, the
measurement happens *during* the gesture, so there is no captured value left to
go stale. This fix protects the window in which the form fields still exist —
which decision 13 already says is one release long. Do not spend effort
hardening it further.

### What was measured and cleared, so nobody re-does it

`measureImageHeight`'s arithmetic, the card's box writing, the keep-ratio clamp,
`imageBoxStyle`, and the browser cache were each eliminated by measurement, not
by reading. The card side was proven correct in a real browser: a portrait image
at `width: 30 %` on a 400×300 layer reported exactly 80, matching the rectangles.
The bug was never in the card.


## Follow-up for a later version: make a live camera honour an explicit height

**Wanted, explicitly, for a future version — not for 1.6.** Recorded here so the
groundwork does not have to be redone; it folds into `follow-ups.md` with a
number when `next` merges.

**What 1.6 does instead.** A live camera forces keep-ratio: the checkbox reads
ticked and disabled, `ha-form`'s own per-field warning explains why at
`camera_view`, and the stored `height` is never touched — leaving Live gives it
back. One predicate, `ratioIsForced` in `src/image-box.ts`, is read by the card,
the element and the form.

**Why it is broken upstream, measured.** `hui-image` keeps its `.ratio` container
for a stream because no `<img>` ever loads to settle `_lastImageHeight`, and that
container is `height: 0` with a padding-bottom. Its rule that fills the padding
box only targets two tag names:

```css
.ratio img, .ratio div { width:100%; height:100%; position:absolute; top:0; left:0 }
```

`ha-camera-stream` is neither, so it resolves `height: 100%` against zero.
Measured on frontend `20260729.6` against a real camera, in a box asked to be
196×49: wrapper 196×49 (ours, correct), `hui-image` 196×49, `.container`
196×110.3 with classes `container ratio fill`, `ha-camera-stream` **196×0**.

**The route the user wants explored.** A `transform: scaleY(k)` on `hui-image` —
which lives in our own shadow root, so it is ours to transform — with
`transform-origin: 0 0` and `k = ourHeight / containerHeight`. Transforms do not
participate in layout, so our box stays correct and only the drawing is squashed.
Non-uniform scaling distorts, which is exactly what an explicit height means
here.

**What it costs, and neither is small:**

- `containerHeight` is only readable by reaching into `hui-image`'s shadow root
  (open, so `huiImage.shadowRoot.querySelector(".container")` works) for a CSS
  class that is no API.
- `k` is a ratio of pixels, so it goes stale on resize — a third
  `ResizeObserver` owed by this line, alongside the one the distortion needs.

**One objection dropped on review:** the scale would also distort any controls
`hui-image` or `ha-camera-stream` draw. The user notes we display none, so this
does not apply to our case.

**Consider filing upstream first.** Adding `ha-camera-stream` to that CSS
selector is one line in Home Assistant and fixes it for everyone; a workaround
here becomes a double correction, silently, the day they ship it.


## Follow-up: a mask that lets clicks through

Raised 2026-08-25 while removing the `pointer-events: none` of the original
decision 8. The wanted shape is a PNG with a transparent hole, through which the
items underneath stay clickable.

**Not possible as CSS stands.** For HTML content only `pointer-events: auto` and
`none` are defined; the pixel-testing values — `visiblePainted`, `painted`,
`visible` — are SVG-only. And the SVG escape hatch does not apply: an SVG loaded
through `<img src>` is a replaced box whose interior is not interactive, and
`hui-image` renders exactly that.

**The one real route is `clip-path`**, which does affect hit-testing — a clipped
element is not a pointer target outside its region. It needs the shape written
out; it cannot be derived from the image's alpha. So it would be a config key
carrying a polygon or a path, not something inferred.

Worth pairing with the live-camera `transform` follow-up above: both are cases
where the honest 1.6 answer was to state a limit rather than work around it.

## Follow-up: the outline stays on the wrong item for the whole drag

Noticed 2026-08-28, while brainstorming the toolbar. Grab item B while item A is
selected: A keeps its selection outline until the pointer is released. Two things
are being read off one value — what the editor has *announced* as selected, and
what the picture *shows* as selected — and only the first is meant to wait.

**The obvious fix is wrong and is already refused in the code.** `onSelect` fires
at the drop, not at `pointerdown`, and `drag-layer.ts` says why at the call site:
announcing a selection opens that item's form, and the dialog scrolls to it —
which carried the picture off the screen with the finger still on the item.
Moving the announcement earlier reintroduces exactly that.

What is owed is the other half: the `.selected` class is applied in
`_applyMarks` straight from `this.selected`, so it inherits the announcement's
delay for no reason. The mark should drop as soon as a gesture starts on a
different item — the card already knows which one, through `_gestureIndex()`,
and `_applyMarks` already consults it for the marker corner and already carries
the comment saying a mark is not a coordinate. The rule wants amending, not the
mechanism.

Not a regression of the resize line: the same holds for a drag, and held before
the handles existed.

## ~~Amendment owed to the resize line: the side handles are the free channel~~ — DESIGNED 2026-08-28, NOT BUILT

Kept below because the reasoning is not recoverable from the diff, and because
the spec argues from it. Two things in it are now out of date and are corrected
in the spec: the shape (squares, not pills) and the completeness of the rule
(decision 10 was missing).

Found 2026-08-28, brainstorming the toolbar. **Independent of the toolbar in both
directions** — neither needs the other — so it is its own branch and its own
amendment to `docs/superpowers/specs/2026-08-26-image-resize-handles-design.md`.

**Resize decision 1 already contains the answer, inverted.** It rejected side
handles because *"a north or south handle has nothing to write while the ratio is
kept — it can only break it"*. Can only break it **is the definition of the free
gesture**. The alleged defect is the function being looked for.

The rule, with no mode and no modifier:

- **corners** — proportional, `width` alone in keep-ratio (unchanged, shipped);
- **sides** — free, one axis each. N/S writes `height`. E/W writes `width` **and
  freezes the current pixel height as an explicit `height`**, otherwise the
  height follows the width in keep-ratio and an E/W handle is indistinguishable
  from a corner.

SHIFT survives unchanged as the pointer shortcut that frees both axes from a
corner — decided during the gesture and forgotten, which is the property a
toolbar toggle cannot have.

**Hidden, not disabled, under `ratioIsForced`** (live camera): SHIFT is already
inert there, and a visible handle that cannot act is a claim the item does not
honour.

~~Shapes, settled: square at the corners, long/pill at the side midpoints — the
conventional arrangement.~~ **Reversed by the user on 2026-08-28: the same square
everywhere, so that eight handles read as one family.** Placement that adapts to
the item's size when handles would crowd a small box is deliberately deferred,
not forgotten.

**What it killed, and this is the point of writing it down.** The toolbar was
going to carry a persistent ratio padlock as the touch channel for free resize.
Two things sank it: a toggle *engraves* a decision for the next gesture where
SHIFT decides *during* it and forgets, which is worse ergonomics for the same
job; and the premise was wrong anyway — touch was never without a channel, since
resize decision 14 kept the form's `width` / `height` fields for exactly the
users a pointer gesture does not serve. Do not reintroduce the padlock.

**One trap carried over:** an E/W handle holding the opposite edge under the
`auto` anchor meets the same self-referential position problem as a corner does —
resize decision 4's closed form, `L = 100 · (R − w) / (W − w)`, one axis at a
time. It does not resolve by guessing.

**What the design changed from what the amendment section above promised**, and
both would otherwise be built wrong:

- **The shape is the corner's square, at the midpoints too.** The pill was
  reversed by the user. Eight handles reading as one family beat the
  conventional arrangement.
- **The floor stays at 24 px, and the intuitive answer is wrong.** Three handles
  per axis looks like it should raise it. It does not, because a handle is
  centred *on* its edge rather than inset: two corners occupy `[-s/2, s/2]` and
  `[W-s/2, W+s/2]`, a midpoint occupies `[W/2-s/2, W/2+s/2]`, and they stay clear
  while `W ≥ 2s` — the bound the corners alone already imposed. I got this wrong
  in the first draft of the spec and corrected it before the commit; do not
  re-derive it from the handle count.
- **Decision 10 was missing from the amendment and is the user's own catch.**
  The gesture's no-change test compares the candidate box to the *stored config*,
  which only ever worked while an absent `height` could mean nothing but an
  unchanged one. A side handle breaks it: pressing an E/W handle freezes a pixel
  height, releasing on the spot faces an absent `storedHeight`, and a number is
  not `undefined` — so an image nobody resized leaves keep-ratio. The test must
  compare to the box **at `pointerdown`**: the stored number where there is one,
  the measured pixel size where there is not. It closes the same hole on a
  corner, reachable today by grabbing, holding SHIFT, wandering, coming back and
  releasing.

**The mechanism, in one line, so a cold reader does not design a second gesture:**
the affine helpers in `src/resize-box.ts` are already written one axis at a time,
so a side handle is the corner gesture with **one axis switched off** — the
per-axis `boolean` widens to `boolean | undefined`, and `undefined` means the
axis asks for nothing, ratchets nothing, bounds nothing, and keeps its
`pointerdown` size and leading edge. Everything else falls out: a side is `free`
by construction, so SHIFT has nothing to free and `lockedScale` is unreachable
from one by structure rather than by a guard.

### The cursor question — SETTLED 2026-08-25, and it shrank on the way

The question was "should the cursor follow *will something happen*". The answer
is **no**, and the rule now written into spec decision 8 is:

> **Our cursor follows Home Assistant's decision, never a forecast of the
> result.** If an action is declared we announce it; a misconfigured one does
> nothing, and HA says so its own way.

A reachability rule was designed in full first — a per-item `actionEntities`
keyed by HA's own action names, a `READS_ACTION_ENTITY` set for the fact that
`more-info` reads the action's own `entity` and `toggle` does not — and then
dropped whole. **What killed it is that it required a copy of `handleAction`'s
table**, pinned to a frontend build and silently wrong the day HA changes it.
Do not revive it without a reason that outweighs that; the reasoning is in the
spec, not only here.

**What replaced it, and why it is smaller.** `src/element-kinds.ts` declares each
kind once: its `stub`, and an optional `defaultActions`. The image declares
`tap_action: none`; the icon and the label declare nothing, **and that absence is
a decision** — it delegates to HA's own more-info default rather than freezing
today's value. The declaration is merged into the config at `setConfig`, which is
Home Assistant's own idiom (`hui-image-element.setConfig` does exactly this,
which is why the card pins `none` on the background), and the merge belongs there
rather than in a helper for a reason worth keeping:

**`relayActions` hands the *stored* config object to `handleAction`.** Resolve
anywhere else and the cursor, the gesture binding (`hasHold` / `hasDoubleClick`)
and what HA actually executes read three different objects. That is the whole
argument, and it is the one thing to re-derive nothing about.

**The editor must never merge.** It *derives* the form's `ui_action`
`default_action` from the same declaration. Merging there would write those keys
back into the user's config on the next save — the selector displays a default,
it does not store one.

**A trap that was avoided rather than met**, worth knowing before touching this:
`handler.bind` is a **one-way door**. There is no unbind, and our elements
survive config changes (the card re-calls `setConfig` on the existing child
without rebuilding it). So binding stays unconditional; only the two
booleans and the cursor are ours to decide. Never gate the `bind` itself.

**What it cost, and it is deliberate:** an image fed by a camera or an image
entity no longer opens more-info unless asked. This **reverses part of
`7cd48ac`**, whose reasoning was correct about HA and wrong about us: a subject
is not an action. `isImageClickable` is gone; all three kinds share `isClickable`.

**What the change also fixed, silently:** the form said `default_action: "none"`
for the image while the card said "clickable if there is a subject". Two files,
two rules, no test between them, and nothing would have caught it.

### The second review, and the bug that a green test was hiding — 2026-08-25

Over `94eb9f1..HEAD`. It confirmed the first review's three fixes and found one
Important issue, fixed by `9ef9a44`. **It is the most instructive thing on this
branch so far:**

`subjectEntity` returned the picture entity for an image and then *fell through*
to `entity`. But `entity` then reached the entity-name path, which runs **before**
the chosen file is ever consulted — so an image with both a file and a
state-driven `entity` was named after the entity. The function's own comment said
the opposite of what its code did.

**The test could not have caught it.** It used `light.a`, absent from the
fixture's `states`, and the entity path needs a state object to fire at all — so
the assertion passed whatever the precedence was. It now uses an entity the
fixture's registry can name, **and it was run against the previous code to
confirm it fails there**. That last step is the one that was missing, and it is
the same shape as `5c99960`: a test asserting a thing that cannot vary.

**Rule this leaves:** when a test guards a *precedence*, it must use inputs that
make every branch reachable. An absent entity does not test priority, it tests
absence.

**`entity` is out of an image row's fallback chain entirely**, settled by the
user and now the rule: on an image it only influences the filter or swaps the
picture through `state_image`, so it is never what the picture IS. An image
nobody has given a picture to reads its **kind label** — through
`elementLabel`, the catalogue's own key, so the row and the picker say the same
word. A first implementation kept `entity` as a last resort; that was dropped
rather than defended.

The chain, in full: `image_entity` → `camera_image` → what the media selector
shows (`metadata.title`, else the path) → the kind's label. Nothing else.

## The live camera's box is a 16:9 guess — found 2026-08-26, upstream PR open

Found by the user during the manual walkthrough of the resize handles, and it is
**not a resize bug**: the selection outline, the `:hover` halo and the handles
all trace the item wrapper, and it is the wrapper that is wrong. It predates this
branch — those first two are untouched by it. Sub-project 2 only made it
impossible to ignore, because four handles on the corners of a box read as a
claim in a way a soft halo does not.

### The mechanism, measured on frontend `20260729.6`

`hui-image` falls back to a hard-coded **56.25 %** padding box when it has no
configured aspect ratio and has not yet measured an image, and marks its
container `.ratio`. What normally replaces that guess is `_onVideoLoad`, which
records `ha-camera-stream.offsetHeight` into `_lastImageHeight` — and
`_lastImageHeight !== undefined` is what drops the `.ratio` class.

**For a camera with no working stream that signal never arrives.**
`ha-camera-stream` declares a `load` event and both its video players fire it
through `fireEvent(this, "load")`; its MJPEG/snapshot fallback `<img>` does not.
So the guess is permanent. Measured on a 600×410 camera in a 600 px card, on a
genuine card rebuild: container **337.5**, picture **410**, unchanged at 1 s, 3 s,
6 s and 10 s.

**Upstream fix, one handler:** the fallback `<img>` fires the event its own
component already declares. PR **home-assistant/frontend#53810**, one commit,
`+6/-0` in `src/components/ha-camera-stream.ts`. Verified by building the
frontend from the patched source and serving it against this dev core: container
342.3, picture 340.3.

**A wrong turn worth not repeating.** The first attempt added `ha-camera-stream`
to `hui-image`'s `.ratio img, .ratio div` selector. Measured insufficient: the
element gets a height and the picture inside still keeps its own ratio, because
the guess is still never replaced. It was committed, pushed, reverted
(`9bade33`, then `efc7552`), and the PR was rewritten.

### What our workaround does, and when it retires

`applyLiveCameraRatio` in `src/card/image-element.ts`: when `ratioIsForced`, read
the camera's `entity_picture`, measure its natural dimensions, and set
`hui-image.aspectRatio` — a public property it already parses. `useRatio` then
becomes true and the container takes the real ratio.

**Behind a guard**: it acts only while the container's computed
`padding-bottom / width` is within `0.002` of `0.5625`, i.e. while `hui-image` is
demonstrably serving its fallback. Cached per camera entity; every failure path
degrades silently to today's behaviour.

**The guard is a race, and both outcomes are correct** — measured on the shipped
frontend and on one built with the upstream fix. If our code reads before the
picture loads, the guard fires and we supply the real ratio. If it reads after,
the class has already dropped, the guard abstains, and upstream's own correction
does the work. Container and picture agree either way.

So the workaround **cannot be made to retire itself** — the pre-load state is
identical with and without the upstream fix. Removing it is a **version
decision**: when the project's Home Assistant floor includes #53810, delete
`applyLiveCameraRatio` and its guard as a block. Until then it costs one image
request per live-camera element.

**One tension to keep in mind:** the image element spec says `aspect_ratio` is
*"the one background key an image element must not take"*. That is about the
config key and the imposed height it defeats; a live camera is already in forced
keep-ratio with no height to defeat, so the property is fair game here. The code
comment says so; do not read it as a broken decision.

### The method lesson, which cost most of a day

**Three verifications in a row came back green and wrong**, each plausible:

1. the first fix was "proved" by **dispatching the `load` event by hand** — the
   very event that never fires on that path. The proof was built around the
   missing piece;
2. both test lanes and a full code review passed a fix that did **nothing in a
   browser**: the guard ran before `hui-image` had rendered its own shadow DOM,
   found no container, and never retried. Neither lane can see that — happy-dom
   has no layout, and the playwright stub rendered synchronously;
3. the upstream fix was first verified through `yarn dev:serve`, where the
   camera picture **never loaded at all**: the frontend builds `/api/...` URLs
   against its own origin and `serve --single` answers them with `index.html`, so
   the browser was loading HTML as an image. It read as "22.4 px tall".

**What actually settles these questions**: build the frontend from source, serve
it against the real core with `/api` and `/auth` redirected there and `/local`
*relayed* (a redirect makes custom-card modules cross-origin and the browser
refuses them for want of CORS — the card then silently never registers), and
measure the real DOM. A throwaway server doing exactly that is about 40 lines.

**And drive the real dashboard card, not a hand-mounted one.** Cards mounted into
a detached host never got `ha-camera-stream` to draw; replacing a card in the
live view did. Several hours of contradictory measurements came from that alone.
